# Unity UI Prefab YAML Creation

## Purpose

Use this skill when asked to create, reconstruct, or modify a Unity UI prefab by writing its `.prefab` UnityYAML representation directly.

The goal is to produce a prefab that Unity can import as a normal editable asset, while preserving:

- Valid UnityYAML document structure
- Correct GameObject/component relationships
- Correct `RectTransform` hierarchy
- Stable internal `fileID` references
- Correct external `{fileID, guid, type}` references
- Compatibility with the project's Unity version and installed UI packages
- Minimal, reviewable changes when editing an existing prefab

This skill targets Unity's GameObject-based UI system, commonly called **uGUI**, including:

- `Canvas`
- `CanvasScaler`
- `GraphicRaycaster`
- `RectTransform`
- `CanvasRenderer`
- `Image`
- `RawImage`
- `Button`
- `Toggle`
- `Slider`
- `ScrollRect`
- `ScrollBar`
- `Mask`
- `RectMask2D`
- Layout groups and layout elements
- Legacy `Text`
- TextMesh Pro UI components when project-derived templates are available
- User-authored `MonoBehaviour` components

Do not use this skill for UI Toolkit `.uxml` or `.uss` files unless the user explicitly requests conversion to uGUI prefab YAML.

---

## Critical Constraint

UnityYAML is not a general-purpose public prefab authoring format. Serialized fields can vary by:

- Unity version
- Package version
- Render pipeline
- Installed modules
- Component implementation
- Script compilation state

Never invent the full serialization layout of a complex component from memory when a project-derived example can be obtained.

Use an **exemplar-first workflow**:

1. Identify the project's Unity version and relevant package versions.
2. Locate or request a small prefab containing each required component type.
3. Copy the component's serialized field structure from that prefab.
4. Replace only values and references required by the requested UI.
5. Let Unity reserialize the imported prefab afterward.

For built-in structural objects such as `GameObject`, `RectTransform`, and `CanvasRenderer`, known templates may be used, but project-derived serialization is still preferred.

---

## Required Inputs

Before generating a prefab, collect as many of the following as are available:

- Target Unity version
- Render pipeline, if relevant
- Whether the project uses uGUI, TextMesh Pro, or both
- Desired hierarchy
- Root canvas behavior
- Target reference resolution
- RectTransform anchors, pivots, sizes, and offsets
- Sprites, fonts, materials, prefabs, and scripts to reference
- Their `.meta` GUIDs and local file IDs
- Existing prefab to modify, when applicable
- A project-generated reference prefab containing required component types

When some inputs are unavailable, use these defaults:

- Create a prefab meant to be placed under an existing Canvas unless a Canvas root is explicitly requested.
- Use stretch anchors for full-panel containers.
- Use centered anchors for fixed-size controls.
- Use pivot `{x: 0.5, y: 0.5}` unless alignment implies otherwise.
- Use local scale `{x: 1, y: 1, z: 1}`.
- Use local rotation quaternion `{x: 0, y: 0, z: 0, w: 1}`.
- Use no external asset reference rather than inventing a GUID.
- Insert clearly named placeholders for missing project GUIDs.

Never guess a GUID.

---

## Source of Truth Priority

Use sources in this order:

1. The exact prefab being edited
2. A prefab generated by the same Unity project
3. A minimal reference prefab generated in the same Unity version and package configuration
4. A serialized example from the exact same component/package version
5. A known structural template for simple built-in components

If two sources disagree, prefer the source generated by the target project.

## UnityYAML Fundamentals

A text-serialized Unity prefab normally begins with:

```yaml
%YAML 1.1
%TAG !u! tag:unity3d.com,2011:
```

Each serialized object is a YAML document with a Unity class ID and a local file ID:

```yaml
--- !u!1 &100000
GameObject:
  ...
```

The general header form is:

```text
--- !u!<classID> &<fileID>
```

Common class IDs used by UI prefabs include:

| Class | Class ID |
|---|---:|
| GameObject | 1 |
| MonoBehaviour | 114 |
| CanvasRenderer | 222 |
| Canvas | 223 |
| RectTransform | 224 |
| CanvasGroup | 225 |

Most uGUI controls such as `Image`, `Button`, `CanvasScaler`, layout groups, and TextMesh Pro components serialize as `MonoBehaviour` documents with class ID `114`. Their exact type is identified by `m_Script`.

---

## Reference Forms

### Internal reference

References another object in the same `.prefab` file:

```yaml
{fileID: 100002}
```

### Null reference

```yaml
{fileID: 0}
```

### External asset reference

References an object in another asset using its `.meta` GUID:

```yaml
{fileID: 21300000, guid: REPLACE_WITH_SPRITE_GUID, type: 3}
```

Do not assume that every sprite uses the same local file ID. Obtain the actual reference from an existing serialized asset or Unity's inspector/debug data.

### Script reference

A `MonoBehaviour` normally identifies its script using:

```yaml
m_Script: {fileID: 11500000, guid: REPLACE_WITH_SCRIPT_GUID, type: 3}
```

Never infer a script GUID from the class name. Read it from the script's `.meta` file.

---

## File ID Rules

Every serialized object in a prefab must have a unique local `fileID`.

Use deterministic IDs so the generated prefab is easy to review and regenerate. A recommended scheme is:

- Reserve a numeric block per GameObject.
- Assign the GameObject first.
- Assign its RectTransform second.
- Assign remaining components afterward.

Example:

| Object | File ID |
|---|---:|
| Root GameObject | 100000 |
| Root RectTransform | 100001 |
| Root CanvasRenderer | 100002 |
| Root Image | 100003 |
| Child GameObject | 101000 |
| Child RectTransform | 101001 |
| Child CanvasRenderer | 101002 |
| Child Text component | 101003 |

Rules:

- IDs must be unique within the file.
- IDs do not need to match Unity-generated random IDs.
- Do not change existing IDs unnecessarily when editing a prefab.
- Do not reuse an ID after deleting a document during the same edit unless all references have been checked.
- Every internal reference must resolve to exactly one document.

Maintain a file-ID registry while generating:

```text
100000 Root GameObject
100001 Root RectTransform
100002 Root CanvasRenderer
100003 Root Image
101000 Label GameObject
101001 Label RectTransform
101002 Label CanvasRenderer
101003 Label TMP_Text
```

## GameObject Structure

A GameObject document owns an ordered list of components:

```yaml
--- !u!1 &100000
GameObject:
  m_ObjectHideFlags: 0
  m_CorrespondingSourceObject: {fileID: 0}
  m_PrefabInstance: {fileID: 0}
  m_PrefabAsset: {fileID: 0}
  serializedVersion: 6
  m_Component:
  - component: {fileID: 100001}
  - component: {fileID: 100002}
  - component: {fileID: 100003}
  m_Layer: 5
  m_Name: Panel
  m_TagString: Untagged
  m_Icon: {fileID: 0}
  m_NavMeshLayer: 0
  m_StaticEditorFlags: 0
  m_IsActive: 1
```

For UI objects:

- Use layer `5` when the project uses Unity's standard UI layer.
- Ensure every component listed in `m_Component` exists.
- Ensure every component points back to this GameObject through `m_GameObject`.
- Preserve component order from a project-generated reference when possible.

## RectTransform Structure

Every uGUI GameObject should normally have one `RectTransform`.

```yaml
--- !u!224 &100001
RectTransform:
  m_ObjectHideFlags: 0
  m_CorrespondingSourceObject: {fileID: 0}
  m_PrefabInstance: {fileID: 0}
  m_PrefabAsset: {fileID: 0}
  m_GameObject: {fileID: 100000}
  m_LocalRotation: {x: 0, y: 0, z: 0, w: 1}
  m_LocalPosition: {x: 0, y: 0, z: 0}
  m_LocalScale: {x: 1, y: 1, z: 1}
  m_ConstrainProportionsScale: 0
  m_Children:
  - {fileID: 101001}
  m_Father: {fileID: 0}
  m_LocalEulerAnglesHint: {x: 0, y: 0, z: 0}
  m_AnchorMin: {x: 0, y: 0}
  m_AnchorMax: {x: 1, y: 1}
  m_AnchoredPosition: {x: 0, y: 0}
  m_SizeDelta: {x: 0, y: 0}
  m_Pivot: {x: 0.5, y: 0.5}
```

Hierarchy invariants:

- A child RectTransform's `m_Father` references the parent's RectTransform, not its GameObject.
- A parent's `m_Children` contains the child RectTransform file IDs.
- Child ordering in `m_Children` determines sibling order.
- The root RectTransform uses `{fileID: 0}` as `m_Father` for a standalone prefab root.
- Every non-root RectTransform must appear once in its parent's `m_Children`.

---

## RectTransform Layout Rules

### Fixed-size centered element

```yaml
m_AnchorMin: {x: 0.5, y: 0.5}
m_AnchorMax: {x: 0.5, y: 0.5}
m_AnchoredPosition: {x: 0, y: 0}
m_SizeDelta: {x: 320, y: 100}
m_Pivot: {x: 0.5, y: 0.5}
```

### Full stretch

```yaml
m_AnchorMin: {x: 0, y: 0}
m_AnchorMax: {x: 1, y: 1}
m_AnchoredPosition: {x: 0, y: 0}
m_SizeDelta: {x: 0, y: 0}
m_Pivot: {x: 0.5, y: 0.5}
```

### Stretch with margins

For stretched axes, Unity represents offsets through `m_AnchoredPosition` and `m_SizeDelta`. Do not casually translate CSS-like left/right/top/bottom margins by intuition. Prefer copying values from a Unity-generated exemplar or compute them using Unity's RectTransform rules.

### Top-left anchored element

```yaml
m_AnchorMin: {x: 0, y: 1}
m_AnchorMax: {x: 0, y: 1}
m_AnchoredPosition: {x: 20, y: -20}
m_SizeDelta: {x: 200, y: 60}
m_Pivot: {x: 0, y: 1}
```

### Bottom-right anchored element

```yaml
m_AnchorMin: {x: 1, y: 0}
m_AnchorMax: {x: 1, y: 0}
m_AnchoredPosition: {x: -20, y: 20}
m_SizeDelta: {x: 200, y: 60}
m_Pivot: {x: 1, y: 0}
```

## CanvasRenderer

Most visible `Graphic` objects require a `CanvasRenderer`:

```yaml
--- !u!222 &100002
CanvasRenderer:
  m_ObjectHideFlags: 0
  m_CorrespondingSourceObject: {fileID: 0}
  m_PrefabInstance: {fileID: 0}
  m_PrefabAsset: {fileID: 0}
  m_GameObject: {fileID: 100000}
  m_CullTransparentMesh: 1
```

Use the exact serialized fields from the target Unity version.

Containers with no visual `Graphic` usually do not require a `CanvasRenderer`.

## MonoBehaviour Components

Most UI behavior and graphics serialize as class ID `114`:

```yaml
--- !u!114 &100003
MonoBehaviour:
  m_ObjectHideFlags: 0
  m_CorrespondingSourceObject: {fileID: 0}
  m_PrefabInstance: {fileID: 0}
  m_PrefabAsset: {fileID: 0}
  m_GameObject: {fileID: 100000}
  m_Enabled: 1
  m_EditorHideFlags: 0
  m_Script: {fileID: 11500000, guid: REPLACE_WITH_SCRIPT_GUID, type: 3}
  m_Name: 
  m_EditorClassIdentifier: 
  ... component-specific fields copied from an exemplar ...
```

Requirements:

- `m_Script` must reference the correct `.cs.meta` GUID.
- Serialized field names must match exactly.
- Preserve `serializedVersion` fields.
- Preserve fields that look redundant; Unity may expect them.
- Do not serialize C# properties that Unity does not serialize.
- Respect `[FormerlySerializedAs]` only through the names Unity currently writes.
- For managed references, prefab overrides, polymorphic data, or complex nested arrays, prefer Editor scripting over manual YAML generation.

## Image Components

For an `Image`, use a project-generated reference block and modify only safe values such as:

- `m_Color`
- `m_RaycastTarget`
- `m_Maskable`
- `m_Sprite`
- `m_Type`
- `m_PreserveAspect`
- `m_FillCenter`
- Fill settings
- Pixels-per-unit multiplier

Do not invent the `Image` script GUID. Obtain it from an existing Image component in the same project or package installation.

For an empty sprite reference:

```yaml
m_Sprite: {fileID: 0}
```

For a project sprite:

```yaml
m_Sprite: {fileID: REPLACE_WITH_LOCAL_SPRITE_FILE_ID, guid: REPLACE_WITH_GUID, type: 3}
```

Use normalized color channels in Unity's serialized color structure, normally ranging from `0` to `1`.

---

## Buttons and Selectables

A typical button GameObject contains:

1. `RectTransform`
2. `CanvasRenderer`
3. `Image`
4. `Button`

Its label is normally a child GameObject.

The Button's target graphic must reference the Image component, not the Image GameObject:

```yaml
m_TargetGraphic: {fileID: 100003}
```

The serialized button event should normally remain empty unless callbacks are explicitly requested:

```yaml
m_OnClick:
  m_PersistentCalls:
    m_Calls: []
```

When wiring a persistent callback:

- The target object reference must be valid.
- The method must be compatible with UnityEvent serialization.
- The method name and argument mode must match Unity's generated structure.
- Prefer copying a callback block produced by Unity.
- Never create an unverified persistent callback structure from memory.

Preserve navigation and transition fields from the exemplar. When unspecified, use the project's default button serialization.

---

## Text and TextMesh Pro

### Legacy Text

Legacy `UnityEngine.UI.Text` may be generated only from a matching exemplar. Ensure its font reference is valid.

### TextMesh Pro

TextMesh Pro component serialization changes across package versions and contains many fields. Always copy a complete `TextMeshProUGUI` component from the target project.

Modify only known fields such as:

- Text content
- Font asset reference
- Font size
- Font style
- Color
- Alignment
- Wrapping and overflow settings
- Raycast target
- Margin

Do not remove unfamiliar TMP fields.

Do not guess:

- TMP script GUID
- Font asset GUID
- Material preset GUID
- Fallback asset references
- Internal font/material local file IDs

For multiline serialized strings, preserve YAML quoting and escaping exactly as Unity writes it.

---

## Layout Components

For components such as:

- `HorizontalLayoutGroup`
- `VerticalLayoutGroup`
- `GridLayoutGroup`
- `ContentSizeFitter`
- `AspectRatioFitter`
- `LayoutElement`

copy the complete MonoBehaviour block from a project-generated exemplar.

When layout components drive child sizing or position:

- Do not simultaneously hard-code contradictory RectTransform values unless Unity normally does so.
- Understand that some stored RectTransform values may be overwritten at runtime or during layout rebuild.
- Preserve child alignment, spacing, padding, control-size, force-expand, and scale-related fields.

---

## Scroll Views

Scroll views contain cross-references among multiple components. Build and validate them as a graph.

Typical structure:

```text
Scroll View
├── Viewport
│   └── Content
├── Horizontal Scrollbar        optional
└── Vertical Scrollbar          optional
```

Typical references include:

- `ScrollRect.m_Content` -> Content RectTransform
- `ScrollRect.m_Viewport` -> Viewport RectTransform
- `ScrollRect.m_HorizontalScrollbar` -> horizontal Scrollbar component
- `ScrollRect.m_VerticalScrollbar` -> vertical Scrollbar component
- `Scrollbar.m_HandleRect` -> Handle RectTransform
- `Scrollbar.m_TargetGraphic` -> Handle Image

Copy the entire ScrollRect and Scrollbar serialization from a same-version exemplar. Verify every cross-reference.

---

## Canvas Root Prefabs

Only add a Canvas root when explicitly requested or required by the target use case.

A screen-space UI root commonly includes:

1. RectTransform
2. Canvas
3. CanvasScaler
4. GraphicRaycaster

An EventSystem is normally a scene-level object and should not be embedded in each UI prefab unless explicitly requested.

Canvas serialization differs depending on render mode and version. Copy it from a project-generated reference.

For reusable windows and panels, prefer a root panel intended to be parented under an existing scene Canvas.

---

## Nested Prefabs and Variants

Nested prefab instances and prefab variants contain structures such as `PrefabInstance`, source-object links, property modifications, and stripped objects.

Do not manually synthesize nested prefab or variant YAML unless:

- An exact same-version exemplar is available, and
- The source prefab GUIDs and source object file IDs are known, and
- The requested modification list is small and well understood.

Otherwise create a standalone unpacked prefab hierarchy, or use a Unity Editor script with `PrefabUtility`.

Never convert an existing nested prefab instance into copied standalone objects silently. State the structural change if it is unavoidable.

---

## Editing Existing Prefabs

When modifying an existing prefab:

1. Parse all document headers and collect class IDs and file IDs.
2. Build maps for:
   - GameObject -> component list
   - Component -> GameObject
   - RectTransform -> parent
   - RectTransform -> children
   - All internal references
3. Identify the smallest required edit.
4. Preserve unrelated field ordering and values.
5. Preserve existing file IDs.
6. Add new IDs without collisions.
7. Update both sides of hierarchy relationships.
8. Re-run all validation checks.

Avoid reformatting the complete file unless necessary. UnityYAML diffs are easier to review when unrelated blocks remain untouched.

## New Prefab Generation Procedure

### Step 1: Produce a UI specification

Translate the request into a hierarchy table:

| Path | Components | Anchors | Position | Size | Notes |
|---|---|---|---|---|---|
| Panel | RectTransform, Image | stretch | 0,0 | 0,0 | background |
| Panel/Header | RectTransform, TMP_Text | top stretch | 0,-24 | 0,64 | title |
| Panel/CloseButton | RectTransform, Image, Button | top-right | -24,-24 | 48,48 | close |

Resolve naming, sibling order, active state, and raycast behavior.

### Step 2: Collect component exemplars

Obtain same-project YAML blocks for every component type.

At minimum, collect examples for:

- Image
- Button
- Text or TMP
- Layout components
- Canvas components when used
- Any custom MonoBehaviour

### Step 3: Allocate file IDs

Create a registry before writing YAML.

### Step 4: Write GameObjects

For each GameObject:

- List all component IDs.
- Set layer and active state.
- Use a unique name.

### Step 5: Write RectTransforms

- Set parent and children references.
- Preserve sibling order.
- Apply anchors, pivot, anchored position, and size.

### Step 6: Write components

- Start from exemplars.
- Replace `m_GameObject`.
- Replace object references.
- Replace requested property values.

### Step 7: Validate graph integrity

Run all checks in the validation section.

### Step 8: Save and import

Write the result as UTF-8 text with a `.prefab` extension under `Assets/`.

Unity should create the `.meta` file when the prefab is first imported. If the prefab must retain a predetermined GUID, create or preserve its `.meta` file explicitly.

### Step 9: Let Unity normalize

Open the project, allow Unity to import the prefab, inspect it, then save it from Unity so the Editor can normalize serialization.

## Validation Checklist

### Document validation

- File starts with the YAML and TAG directives.
- Every document header has a valid class ID and unique file ID.
- No duplicate local file IDs exist.
- YAML indentation is consistent.
- No tabs are used for indentation.
- Every referenced internal file ID exists.

### GameObject/component validation

- Every component in `m_Component` exists.
- Every listed component points back to the owning GameObject.
- Every component belongs to exactly one GameObject unless the serialized format explicitly says otherwise.
- Every UI GameObject has exactly one RectTransform.
- Visible Graphic objects have a CanvasRenderer when required.

### Hierarchy validation

- Exactly one root RectTransform exists for a standalone prefab.
- Root `m_Father` is null.
- Every non-root RectTransform has one valid parent.
- Every child appears in the parent's `m_Children` list.
- Every entry in `m_Children` points back to that parent.
- No transform cycles exist.
- Sibling order matches the requested hierarchy.

### External reference validation

- Every GUID contains exactly 32 hexadecimal characters when finalized.
- Every external reference uses the correct local file ID.
- Every script GUID matches its `.cs.meta` file.
- No placeholder GUID remains in final production output.

### UI semantic validation

- Button target graphic points to a Graphic component.
- ScrollRect references RectTransforms and scrollbar components correctly.
- Mask and viewport relationships are coherent.
- Raycast targets are disabled on decorative graphics when appropriate.
- Stretch and fixed-size anchor configurations are intentional.
- Layout groups do not conflict with manually positioned children.
- TMP font and material references belong to compatible assets.

### Import validation

After importing in Unity:

- No console deserialization errors appear.
- The prefab opens in Prefab Mode.
- The hierarchy is complete.
- Components are not shown as Missing Script.
- Visual assets resolve.
- Buttons and controls are interactable.
- RectTransforms behave correctly at multiple resolutions.
- Saving the prefab does not remove or radically rewrite unintended data.

## Automated Static Validation

When code execution is available, validate generated YAML before delivery.

A validator should at least:

1. Extract every document file ID using a document-header pattern.
2. Reject duplicate IDs.
3. Extract every `{fileID: N}` internal reference without a GUID.
4. Report unresolved nonzero references.
5. Parse each GameObject component list.
6. Verify each component's `m_GameObject` backlink.
7. Parse RectTransform `m_Father` and `m_Children` relationships.
8. Detect hierarchy asymmetry and cycles.
9. Find unresolved placeholder tokens such as `REPLACE_WITH_`.
10. Confirm GUID formatting.

Static validation cannot guarantee import compatibility. Unity Editor import remains the final authority.

---

## Safer Alternative: Editor Script Generation

Recommend a Unity Editor script instead of direct YAML when the prefab requires:

- Nested prefabs or variants
- Complex UnityEvents
- Managed references
- Animation clips or Animator bindings
- Complex TMP configuration without an exemplar
- Version-unknown serialization
- Many custom scripts
- Dynamic asset lookup
- Reliable undo, prefab connection, and import behavior

A safe Editor-script workflow is:

1. Create GameObjects and components through Unity APIs.
2. Configure RectTransforms and serialized properties.
3. Resolve assets with `AssetDatabase`.
4. Save with `PrefabUtility.SaveAsPrefabAsset`.
5. Allow Unity to generate canonical YAML.

When the user explicitly asks for YAML, still use YAML where practical, but explain any component that must be generated through an Editor script.

## Output Contract

When completing a request with this skill, provide:

1. The generated `.prefab` file or a precise patch to the existing prefab.
2. A concise hierarchy summary.
3. A list of unresolved placeholders, if any.
4. Any required asset GUID/fileID mapping.
5. Validation results.
6. A warning when Unity import testing was not possible.

Do not claim a prefab is import-valid unless it was actually imported successfully in a compatible Unity project.

## Decision Rules

- If an existing prefab is supplied, patch it instead of rebuilding it.
- If a required GUID is absent, use a placeholder and report it.
- If a component exemplar is absent, do not fabricate complex serialization.
- If a simple standalone hierarchy is requested, generate direct YAML.
- If nested prefab behavior is requested, prefer an Editor script.
- If the user asks for production-ready output, require or derive all GUID mappings and perform validation.
- If import testing is unavailable, say that the result is statically validated but not Unity-import tested.

---

## Quality Standard

A high-quality result is not merely syntactically valid YAML. It must also be a coherent Unity object graph whose serialized data matches the target project's component versions.

Prioritize, in order:

1. No data corruption
2. Correct references
3. Correct hierarchy
4. Project/version compatibility
5. Minimal diffs
6. Requested visual layout
7. Readability of generated YAML
